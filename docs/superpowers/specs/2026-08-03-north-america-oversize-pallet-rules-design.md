## 1. 设计结论

本设计不新建第二套算托系统，而是在现有货物明细、报价 API、Zone Quote Engine、规则配置和报价版本链路中，重做北美超大件的算托规则。

核心结论如下：

1. 采用“双层计算”：内部计算实体地板占位和车辆可装性，对外只展示最终计费托数。
2. 计算基准是实际搬运单元，不是客户总箱数。总箱数只做数量核对，绝不直接参与托位乘法。
3. 标准托盘统一为 `48×40 in`，即 `121.92×101.6 cm`；允许在车厢地板上旋转 90°，不允许侧翻或改变承重底面。
4. 首次扩托触发线为地板长边 `≥150 cm` 或短边 `≥122 cm`。低于触发线的超出通过固定附加费处理，不直接增加托位。
5. 进入扩托后，方向跨度按标准托盘的真实 `121.92×101.6 cm` 继续计算；首次触发线不能被当成第一托的覆盖长度。
6. 后续标准托位整数边界保留 `5 cm` 容差；容差内不加托，只收轻度边界超出费。
7. 双向超尺寸不能简单用“长向托数×短向托数”。尺寸托数取方向跨度和底面积当量的最大值，面积整数边界保留 `2%` 容差。
8. 重量当量保留为 `500 kg/计费托`。重量可以提高计费托数，但不会把一个完整搬运单元拆成多个实体搬运单元。
9. 可叠放只减少内部地板占位，不减少计费托数。未明确可叠放时按不可叠放做车辆校验，但不因此阻止自动报价。
10. 高板允许自动报价：高度 `≤180 cm` 正常，`>180–210 cm` 收高板费，高于 `210 cm` 转人工。
11. 车辆校验同时检查单件可装性、二维地板排布、总体积和总重量。不得再用“车厢体积÷2 CBM”生成虚拟托盘。
12. 车型采用可配置暂行规划值：26 尺常规 12 托、紧密 14 托；53 尺常规 26 托、紧密 30 托。混合尺寸以真实排布为准。
13. 成功时普通结果只展示“计费托数：N”；无法可靠计算时只展示“需要人工确认”。车辆、附加费和计算过程仅进入内部报价链路与审计记录。

## 2. 目标与非目标

### 2.1 目标

- 消除“少数超长件×客户总箱数”导致托数爆炸的历史问题。
- 对轻微超尺寸、明显超大、重货、高板和可叠放货物给出稳定、可解释、可配置的处理。
- 让托位扩展受实际搬运单元、实际尺寸和真实车辆容量约束。
- 同一输入和同一规则版本始终得到相同结果。
- 在没有供应商正式分档时提供一套可运营、可替换的北美暂行默认值。
- 保留完整内部计算依据，同时保持普通结果极简。

### 2.2 非目标

- 不做随机或不可解释的三维装车优化。
- 不计算车轴载荷、重心、绑扎方案、车门净开口或特殊吊装方案。
- 不允许系统推断侧放、斜放或改变货物承重底面。
- 不让 AI 补造缺失尺寸、单重、箱数、叠放能力或装卸条件。
- 不把车辆数量、附加费明细或内部地板占位展示在普通算托结果中。
- 不在本设计阶段实现代码；实现必须另行编写并批准实施计划。

## 3. 核心概念

### 3.1 客户件数

客户原始询价中的箱、件数量，例如“100 箱”。该数字只用于与搬运单元明细所含箱数核对，不直接参与托位计算。

### 3.2 实际搬运单元

承运和装卸时不可再拆分的最小单位，例如一个已经打好的托盘、一个木箱或一个独立裸件。

示例：

- 100 箱已经打成 2 个托盘：实际搬运单元数量为 2。
- 7 个独立木箱：实际搬运单元数量为 7。
- 36 箱中只有 7 个独立长件：超长扩托只作用于这 7 个长件。

### 3.3 实体地板占位

内部车辆排布所使用的占位。不可叠放或叠放状态未知时，每个搬运单元分别参与地板排布；明确可叠放并满足约束时，可以组成垂直堆叠列，只让最底层占用地板。

实体地板占位仅用于车辆校验，不作为普通结果展示。

### 3.4 尺寸计费托数

根据每个搬运单元的地板长宽和本规格的尺寸分档计算，再乘实际搬运单元数量后汇总。

### 3.5 重量计费托当量

整票计费重量按 `500 kg/托` 向上取整得到的计费托数。

### 3.6 最终计费托数

尺寸托数、重量托数和客户明确申报托数三者的最大值。它是普通结果唯一展示的数字。

### 3.7 高板与叠托

- 高板：货物已经固定在一个底座上并打高，仍是一个实际搬运单元。
- 叠托：两个或多个已经完成的搬运单元在车内上下堆放。

两者不能混为一谈。高板按实际单元高度处理；叠托只在明确确认后减少内部地板占位。

## 4. 输入数据契约

### 4.1 搬运单元明细

每条明细表达一组属性完全相同的实际搬运单元，至少包含：

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `handling_unit_quantity` | 是 | 正整数；表示搬运单元数量，不是客户箱数 |
| `packaging_type` | 是 | 托盘、木箱、裸件、纸箱组合等受控枚举 |
| `length`、`width`、`height` | 是 | 单个搬运单元外部尺寸，必须带明确单位 |
| `unit_gross_weight` | 是 | 单个搬运单元毛重，必须带明确单位 |
| `contained_customer_pieces` | 否 | 该行全部搬运单元合计包含的客户箱/件数，仅用于核对 |
| `stackability` | 是 | `stackable`、`non_stackable`、`unknown`；缺省归一为 `unknown` |
| `max_stack_layers` | 条件必填 | 仅 `stackable` 时用于减少地板占位 |
| `max_top_load_kg` | 条件必填 | 仅 `stackable` 时用于减少地板占位 |
| `floor_rotation_allowed` | 否 | 默认 `true`；只允许在地板上旋转 90°。为 `false` 时保留原始长宽方向 |

尺寸一律表达客户实际交付状态。不得把整行总重量误填为单个搬运单元重量。

### 4.2 订单级字段

- 客户申报总箱/件数，可选。
- 客户申报总重量，可选，但提供时必须带单位。
- 客户申报总体积，可选，但提供时必须带单位。
- 客户明确申报托数，可选，只作为计费下限和核对依据。
- 报价币种。
- 车辆类型，或选择自动匹配。

### 4.3 数据权威边界

- 托位主计算只使用实际搬运单元明细。
- 客户总箱数不参与尺寸托位乘法。
- 客户申报总重量和明细重量同时存在时，容差内取较大值计费。
- 客户申报总体积和尺寸推导体积只用于车辆容量与异常核对，不直接换算计费托。
- 客户明确申报托数不能压低系统尺寸或重量结果。
- AI 可以提取客户明确提供的信息，但不得生成未提供的字段值。

## 5. 单位、方向与数值精度

1. 服务端统一换算为厘米、千克和立方米后计算。
2. 金额使用报价币种，不在本规则中做跨币种换算。
3. 尺寸比较必须使用十进制定点数或等价精确表示，不能让二进制浮点误差改变 `150`、`122`、`5` 等边界结果。
4. 计费分档使用归一后的地板两边：

```text
floor_long  = max(length, width)
floor_short = min(length, width)
```

5. 实际装车排布必须同时保留客户输入的原始 `length/width`：

   - `floor_rotation_allowed=true` 时，允许朝向集合为 `(length,width)` 和 `(width,length)`。
   - `floor_rotation_allowed=false` 时，只允许 `(length,width)`，其中原始 `length` 沿车厢纵向、原始 `width` 沿车厢横向；如果客户不能确认受限朝向，转人工，不能用归一后的长短边猜测。
   - 高度始终是垂直方向，不能通过旋转长宽来改变高度。

6. 标准托盘常量为：

```text
PALLET_LONG_CM  = 121.92
PALLET_SHORT_CM = 101.60
PALLET_AREA_CM2 = 121.92 × 101.60 = 12,387.072
```

## 6. 单个搬运单元尺寸规则

### 6.1 首次扩托前的业务分档

按顺序命中第一条规则：

| 条件 | 单个搬运单元尺寸托数 | 足迹附加费 |
| --- | ---: | ---: |
| `floor_long ≤121.92` 且 `floor_short ≤101.6` | 1 | 0 |
| 超出标准，且 `floor_long ≤135`、`floor_short ≤110` | 1 | 25 |
| 未命中前两档，且 `floor_long <150`、`floor_short <122` | 1 | 50 |
| `floor_long ≥150` 或 `floor_short ≥122` | 进入扩托 | 由扩托边界规则决定 |

`150 cm` 和 `122 cm` 只是从一托进入扩托计算的触发线，不是第一托的覆盖长度。

### 6.2 扩托后的计费有效尺寸

配置值：

```text
LONG_EXPANSION_TRIGGER_CM  = 150
SHORT_EXPANSION_TRIGGER_CM = 122
REPEATED_BOUNDARY_GRACE_CM = 5
```

一旦任一方向达到首次扩托触发线，先对长、短两个方向分别计算“计费有效尺寸”：

```text
effective_axis(dimension, pallet_dimension):
    completed_slots = floor(dimension / pallet_dimension)
    remainder = dimension - completed_slots × pallet_dimension

    if completed_slots ≥ 1 and 0 < remainder ≤ 5 cm:
        return completed_slots × pallet_dimension, boundary_grace_hit=true

    return dimension, boundary_grace_hit=false
```

因此：

```text
effective_long, long_grace_hit
    = effective_axis(floor_long, 121.92)

effective_short, short_grace_hit
    = effective_axis(floor_short, 101.60)

long_slots  = ceil(effective_long / 121.92)
short_slots = ceil(effective_short / 101.60)
```

5 cm 容差只作用于扩托后的标准托位整数边界。例如两托长向标准覆盖为 `243.84 cm`，容差上限为 `248.84 cm`；它不能把两托上限扩大到 `150+121.92=271.92 cm`。

计费有效尺寸只用于托数和边界附加费。车辆可装性和二维排布始终使用客户提供的真实外部尺寸，不能把 5 cm 超出从真实装车模型中删除。

### 6.3 扩托边界附加费

如果任一方向的真实尺寸满足：

```text
n × pallet_dimension < dimension
≤ n × pallet_dimension + 5 cm
```

则该方向的计费有效尺寸压回 `n×pallet_dimension`，该搬运单元保持 `n` 个方向托位，同时命中轻度边界超出费 25。

长、短两个方向同时命中边界容差时，仍属于同一“足迹超出”类别，只收一次 25，不重复累加。

超过 5 cm 后增加下一托位，不再因这个方向收边界超出费。

### 6.4 底面积当量与 2% 容差

进入扩托后，使用第 6.2 节得到的计费有效尺寸计算：

```text
area_ratio = effective_long × effective_short / PALLET_AREA_CM2
lower_integer = max(1, floor(area_ratio))

if area_ratio ≤ lower_integer × 1.02:
    area_slots = lower_integer
else:
    area_slots = ceil(area_ratio)
```

2% 容差表示相对于整数 `n` 的比例容差：面积当量不超过 `n×1.02` 时仍按 `n`，不是固定减去 `0.02` 托。它不覆盖 150/122 cm 首次触发线，也不替代方向跨度校验，并且不单独产生附加费。

先应用 5 cm 方向容差、再使用计费有效尺寸计算面积，保证方向容差不会被原始面积再次推翻。例如 `248.84×101.6 cm` 必须保持 2 托并收一次边界费，不能被面积规则推成 3 托。

### 6.5 单件尺寸托数

未进入扩托时按 6.1 的一托分档执行。进入扩托后：

```text
unit_size_pallets = max(
    2,
    long_slots,
    short_slots,
    area_slots
)
```

不得使用 `long_slots × short_slots`，因为这种完整矩形网格假设会把 `200×130 cm` 木箱错误算成 4 托。

### 6.6 已批准的关键尺寸示例

| 单个搬运单元地板尺寸 | 单件尺寸托数 | 足迹处理 |
| --- | ---: | --- |
| `121.92×101.6 cm` | 1 | 标准 |
| `122×102 cm` | 1 | 轻度超出费 25 |
| `149×121 cm` | 1 | 中度超出费 50 |
| `150×100 cm` | 2 | 首次扩托 |
| `243×100 cm` | 2 | 无边界费 |
| `245×100 cm` | 2 | 超过 243.84 cm 但在 5 cm 内，边界费 25 |
| `248.84×100 cm` | 2 | 容差上边界，边界费 25 |
| `248.84×101.6 cm` | 2 | 先压回两托有效长度再算面积，边界费 25 |
| `249×100 cm` | 3 | 超出两托容差 |
| `273×100 cm` | 3 | 三托 |
| `150×122 cm` | 2 | 首次双向触发，面积不足三托 |
| `200×130 cm` | 3 | 面积约 2.10 托，超过两托 2% 容差 |
| `230×150 cm` | 3 | 面积约 2.78 托 |
| `200×200 cm` | 4 | 面积约 3.23 托 |

## 7. 数量汇总规则

每条搬运单元明细：

```text
line_size_pallets
= unit_size_pallets × handling_unit_quantity
```

整票尺寸托数：

```text
total_size_pallets = sum(line_size_pallets)
```

禁止使用以下任一做法：

- `客户总箱数 × 单件尺寸托数`
- `全票件数 × 超长倍数`
- 因全票存在一个长件而把所有明细统一乘 2

历史回归案例必须固定为：36 个客户箱/件中只有 7 个实际长件时，只对 7 个长件扩托；若每个长件为 2 托，则长件合计为 14 托，不得得到 72 托。

## 8. 重量、高度与附加费

### 8.1 重量计费托

明细重量：

```text
derived_total_weight_kg
= sum(unit_gross_weight × handling_unit_quantity)
```

容差内存在客户申报总重量时：

```text
calculation_weight_kg
= max(derived_total_weight_kg, declared_total_weight_kg)
```

重量计费托：

```text
weight_pallets = ceil(calculation_weight_kg / 500)
```

重量托数只影响最终计费托数，不改变实际搬运单元数量或单件地板矩形。

### 8.2 单件重量分档

| 单个搬运单元重量 | 处理 |
| --- | --- |
| `≤500 kg` | 正常 |
| `>500 kg` 且 `≤1,000 kg` | 自动计算，重货费 75 |
| `>1,000 kg` | 转人工确认装卸设备和承运能力 |

`1,000 kg` 本身仍可自动计算并收重货费；超过 `1,000 kg` 才转人工。

### 8.3 高度分档

| 单个搬运单元高度 | 处理 |
| --- | --- |
| `≤180 cm` | 正常 |
| `>180 cm` 且 `≤210 cm` | 高板费 50，不增加地板或尺寸托数 |
| `>210 cm` | 转人工确认车型、车门和固定方式 |
| 超过所选车辆有效高度 | 单件不可装，转人工或更换车型 |

高板允许在一个托盘底座上继续打高。系统不能用“车厢还能向上装”作为自动叠托依据。

### 8.4 固定附加费

所有金额跟随报价币种，规则版本不做汇率换算：

| 类别 | 暂行默认值/实际搬运单元 |
| --- | ---: |
| 轻度超底盘或扩托边界容差 | 25 |
| 中度超底盘 | 50 |
| 高板 | 50 |
| 重货 | 75 |

同一类别命中多个档位时只收最高档；不同类别可以叠加。例如一个轻度超底盘、190 cm 高、700 kg 的单元内部附加费为 `25+50+75`。

每条明细必须先计算单个搬运单元的各类附加费，再乘实际搬运单元数量：

```text
unit_surcharge
= highest_footprint_surcharge
 + high_pallet_surcharge
 + heavy_unit_surcharge

line_surcharge
= unit_surcharge × handling_unit_quantity

total_surcharge = sum(line_surcharge)
```

不得把一条数量大于 1 的搬运单元明细只收一次附加费。

达到首次扩托线后，不再收首次扩托前的轻度/中度超底盘费；只有命中后续 5 cm 边界容差时收足迹边界费。高板费和重货费仍可叠加。

附加费进入内部报价金额，不改变计费托数，也不在普通算托结果中展开。

## 9. 可叠放与实体地板占位

### 9.1 状态处理

| 状态 | 内部车辆处理 | 对计费托数的影响 |
| --- | --- | --- |
| `unknown` | 按不可叠放 | 不减少 |
| `non_stackable` | 每个搬运单元独立占地 | 不减少 |
| `stackable` 且资料不完整 | 降级为不可叠放 | 不减少 |
| `stackable` 且资料完整 | 允许组成垂直堆叠列 | 不减少 |

资料完整至少包括最大叠放层数和顶部承重能力。

### 9.2 自动叠放范围

暂行版本只自动叠放同一明细中包装类型、地板尺寸、高度和重量相同的搬运单元，不跨明细寻找组合。

候选叠放层数同时受以下条件限制：

- 不超过客户明确确认的 `max_stack_layers`。
- 底层顶部承重足以承受其上所有层的总重量。
- 叠放后的总高度不超过 `210 cm`。
- 叠放后的总高度不超过所选车辆有效高度。

如果某个叠放方案超过 210 cm、超过车辆高度或超过顶部承重，系统必须先减少叠放层数；仍不满足时放弃叠放，并把这些搬运单元按不可叠放重新排车。只有单个实际搬运单元本身超过自动边界，或回退到不可叠放后仍无法装载时，才转人工。不能因为一个可选叠放方案失败而直接阻断本来可以平放运输的货物。

### 9.3 双层数量差异

例如两个轻型标准托明确可以叠成两层：

- 实际搬运单元数量：2。
- 内部地板列数：1。
- 尺寸计费托数：仍为 2。
- 重量计费托数：按两托总重量计算。

系统模拟叠托后总高度超过 180 cm，不会把客户实际交付的两个普通托盘改认成高板，也不会新增高板费。

## 10. 最终计费托数

整票最终公式：

```text
final_billing_pallets = max(
    total_size_pallets,
    ceil(calculation_weight_kg / 500),
    declared_pallet_count or 0
)
```

规则：

- 结果必须是正整数；没有有效搬运单元时不能自动计算。
- 客户明确申报托数只作下限，不能覆盖更高的尺寸或重量结果。
- 可叠放不降低 `total_size_pallets`。
- 体积不直接进入 `final_billing_pallets`。
- 车辆数量不乘以 `final_billing_pallets`。
- 固定附加费不改变 `final_billing_pallets`。

已批准示例：

| 场景 | 尺寸托数 | 重量托数 | 最终计费托数 |
| --- | ---: | ---: | ---: |
| 100 箱打成 2 个标准托，总重 1,800 kg | 2 | 4 | 4 |
| 1 个 `200×130 cm`、900 kg 木箱 | 3 | 2 | 3 |
| 1 个 `122×102 cm`、600 kg 单元 | 1 | 2 | 2 |
| 7 个 `150×100 cm`、每个 200 kg 长件 | 14 | 3 | 14 |
| 客户申报 8 托，系统尺寸为 6 托 | 6 | 视重量 | 至少 8 |

## 11. 车辆规划配置

### 11.1 暂行默认值

| 车型 | 内部有效尺寸 | 有效体积上限 | 载重上限 | 标准托常规值 | 标准托紧密上限 |
| --- | --- | ---: | ---: | ---: | ---: |
| 26 尺非 CDL | `762×243.84×243.84 cm` | `45.3 m³` | `4,536 kg` | 12 | 14 |
| 26 尺 CDL | `762×243.84×243.84 cm` | `45.3 m³` | `7,711 kg` | 12 | 14 |
| 53 尺 Dry Van | `1,600.2×250.19×279.4 cm` | `110.4 m³` | `19,958 kg` | 26 | 30 |

这些是保守规划值，不代表所有供应商车辆完全一致。尺寸、体积、载重、常规值和紧密上限都必须位于可发布配置中。

26/14 和 53/30 是标准 `48×40 in` 托盘在暂行地板尺寸上的紧密几何上限；混合尺寸货物不生硬套用这个整数上限，而以真实矩形排布为准。

### 11.2 依据边界

- Hyundai Translead Original 53 尺干货车官方资料给出约 `52'6"×98.5"×110"` 的内部尺寸和 `3,950 ft³` 体积；本设计把有效体积保守下调为 `3,900 ft³ / 110.4 m³`。

  来源：[Hyundai Translead — Original Dry Van](https://www.hyundaitranslead.com/product/dry-van/original/)
- Penske 22–26 尺箱式车官方资料给出最高约 `25'11"×8'1"×8'7"`、`1,700 ft³`、非 CDL 最高 `10,000 lb` 载重；本设计采用 `300×96×96 in`、`1,600 ft³` 的保守尺寸/体积。

  来源：[Penske — 22–26 Foot Box Truck](https://www.pensketruckrental.com/commercial-truck-rental/commercial-trucks/medium-duty-trucks/22-26-foot-box-truck/)
- Penske CDL 版本官方资料给出最高 `17,000 lb` 载重。

  来源：[Penske — CDL 22–26 Foot Box Truck](https://www.pensketruckrental.com/commercial-truck-rental/commercial-trucks/medium-duty-trucks/22-26-foot-box-truck-cdl-required/)
- 53 尺 `44,000 lb` 是暂行运营规划载重，不是对所有车型和承运商的保证；供应商规则应覆盖它。

## 12. 实际车辆校验

### 12.1 四个必须同时通过的约束

1. **单件可装性**：每个地板列在允许方向下能够放进车辆长宽，列高能够放进车辆高度。
2. **二维地板排布**：所有地板列的真实外部长宽能够无重叠排入车厢地板。
3. **总体积**：分配给每辆车的体积不超过有效体积上限。
4. **总重量**：分配给每辆车的重量不超过载重上限。

任一约束不通过，该车辆方案即不成立。

### 12.2 地板排布

- 每个不可叠放搬运单元是一个真实长宽矩形。
- 每个合法叠放列只用底层单元的真实长宽作为地板矩形。
- 只尝试第 5 节定义的允许朝向；禁止旋转时不得用归一后的长短边代替原始方向。
- 使用确定性的矩形排布方法，至少以面积、长边和短边等固定顺序分别尝试，并选择车辆最少的稳定结果。
- 不使用随机种子或不稳定遍历顺序。

每个候选车辆或车组的地板排布必须返回三态之一：

| 状态 | 含义 | 后续处理 |
| --- | --- | --- |
| `FIT` | 找到满足全部方向和无重叠条件的确定方案 | 继续体积、重量及方案比较 |
| `PROVEN_NOT_FIT` | 单件硬尺寸、总面积下界或确定性证明表明不可能装下 | 才允许尝试更大车型或更多车辆 |
| `INCONCLUSIVE` | 启发式未找到方案，但没有证明一定装不下 | 立即转人工，不能用更贵车型或更多车辆掩盖算法不确定性 |

单纯“没有找到排布”不等于 `PROVEN_NOT_FIT`。如果排布算法未找到方案，但总面积、体积和重量表明理论上可能装下，必须返回 `INCONCLUSIVE`。

### 12.3 体积与重量

- 搬运单元推导总体积为 `sum(length×width×height×handling_unit_quantity)`；叠放不会减少货物总体积。
- 容差内同时存在申报总体积和尺寸推导总体积时，定义 `calculation_total_volume=max(declared_total_volume, derived_total_volume)`；只有一个值时使用现有值。
- 车辆重量使用本规格第 8.1 节的 `calculation_weight_kg`。
- 车辆载重只校验总量；轴载、重心和绑扎属于本版本非目标。

当采用的整票重量或体积高于搬运单元明细推导合计时，差额必须按各搬运单元的推导值等比例分配，生成仅用于车辆容量校验的分配值：

```text
vehicle_check_unit_weight
= derived_unit_weight
 × calculation_weight_kg / derived_total_weight_kg

vehicle_check_unit_volume
= derived_unit_volume
 × calculation_total_volume / derived_total_volume
```

比例计算使用精确十进制值，在最终比较前不逐件取整；各搬运单元分配值之和必须严格等于采用的整票值。这个比例缩放不改变客户提供的单件重量，不改变 500/1,000 kg 单件分档，也不改变计费托数，只解决多车时差额归属。

### 12.4 自动选车和扩车

自动匹配顺序：

1. 尝试一辆 26 尺非 CDL。
2. 重量超过非 CDL 上限时尝试一辆 26 尺 CDL。
3. 一辆 26 尺装不下时先尝试一辆 53 尺，不直接跳成两辆 26 尺。
4. 一辆 53 尺仍装不下时，才拆分为多辆车。
5. 多车方案枚举最多 3 辆车内的可行组合，并使用下面的固定决胜顺序。
6. 最多自动拆分 3 辆车；需要 4 辆或更多时转人工。

以上“装不下”必须是 `PROVEN_NOT_FIT`。任一较小候选返回 `INCONCLUSIVE` 时立即转人工，不继续尝试更大或更多车辆。

同一批货物存在多个 `FIT` 方案时，依次比较：

1. 车辆数量最少。
2. 如果所有候选都有同币种、同口径的已发布车辆基础价，运输基础价合计最低。
3. 总标称有效体积最小。
4. 总标称载重能力最小。
5. 按车辆配置中的稳定 `vehicle_profile_code` 排序后，编码序列字典序最小。

任何一层已经得出唯一方案即停止比较；缺少可比较车辆价格时直接跳过第 2 层。车辆组合枚举、搬运单元排序和相同值决胜都必须使用稳定标识，保证相同输入和规则版本总是选择同一方案。

标准托普通/紧密处理：

- 26 尺 12 托以内、53 尺 26 托以内为普通装载。
- 26 尺 13–14 托、53 尺 27–30 托在四项校验全部通过时仍是一辆车，只标记内部紧密装载状态。
- 31 个不可叠放标准托需要多车，但最终计费托数仍是 31，不因两辆车再次相乘。

单件本身无法放进任何车辆时，增加车辆数量没有意义，直接转人工。

## 13. 数据核对与人工确认

### 13.1 容差计算

两值差异统一按以下方式判断：

```text
allowed_difference = max(
    absolute_tolerance,
    percentage_tolerance × max(abs(value_a), abs(value_b))
)
```

只有 `abs(value_a - value_b) > allowed_difference` 时才算超过容差。

| 核对项目 | 绝对容差 | 比例容差 | 容差内处理 | 超过容差 |
| --- | ---: | ---: | --- | --- |
| 客户总箱数与完整明细所含箱数 | 2 箱 | 5% | 继续，箱数不参与托位 | 转人工 |
| 客户总重量与明细重量合计 | 50 kg | 5% | 采用较大值 | 转人工 |
| 客户总体积与尺寸推导体积 | 0.5 m³ | 10% | 采用较大值做车辆校验 | 转人工 |

如果搬运单元未填写所含客户箱数，或只有部分明细填写，则跳过完整箱数核对并记录内部缺失标记，不用客户总箱数反推。

### 13.2 必须转人工的情况

- 超大件缺少实际搬运单元数量或长宽高。
- 缺少单个搬运单元重量。
- 单个搬运单元重量 `>1,000 kg`。
- 单个搬运单元高度 `>210 cm`。
- 尺寸或重量单位不明确。
- 单件无法装入任何已配置车辆。
- 真实排布无法确认能否装下。
- 数据核对差异超过第 13.1 节容差。
- 自动拆分需要 4 辆或更多车辆。
- 找不到已发布且适用于当前范围的车辆或收费规则版本。
- 计算过程中出现非正数量、非正尺寸、非正重量或其他无效值。

### 13.3 不直接阻断的情况

- 可叠放状态未知：按不可叠放。
- 声明可叠放但缺少层数或承重：按不可叠放。
- 未填写所含客户箱数：跳过箱数核对。
- 客户申报托数低于系统结果：采用系统较高结果。

## 14. 输出与内部审计

### 14.1 普通结果

自动计算成功时，普通页面只展示：

```text
计费托数：N
```

不能可靠自动计算时只展示：

```text
需要人工确认
```

人工场景不得向普通用户展示一组推测托数。

### 14.2 不在普通结果中展示

- 实体地板占位托数或矩形数。
- 车辆类型、数量和紧密装载状态。
- 尺寸托数、重量托数和客户申报托数的分解。
- 附加费类别和金额。
- 规则版本、容差、装车排布和人工触发原因。

### 14.3 内部计算记录

为报价定价、复算和审计，内部必须保存：

- 原始输入和单位。
- 归一后的搬运单元明细。
- 每行尺寸档位、方向托数、面积托数、边界费和行托数。
- 总尺寸托数、重量托数、客户申报托数及最终最大值。
- 高板、重货和足迹附加费。
- 叠放决策和内部地板列。
- 车辆配置版本、排布结果、体积和重量校验。
- 自动成功或人工确认状态及原因代码。
- 完整规则版本和配置快照。

普通销售/客户 DTO 必须通过 allowlist 只暴露最终计费托数或人工状态，不泄露内部定价和供应商信息。

## 15. 配置与版本管理

### 15.1 必须配置化的参数

- 标准托盘长、短边。
- 轻度和中度超尺寸边界。
- 首次扩托长、短边触发线。
- 后续边界容差。
- 面积整数容差。
- `500 kg/计费托` 重量当量。
- 重货起点和人工重量线。
- 正常、高板和人工高度线。
- 所有固定附加费和币种策略。
- 车辆有效长宽高、体积、载重、普通托位和紧密上限。
- 数据核对容差。
- 最大自动车辆数量。

### 15.2 规则优先级

1. 具体供应商＋具体服务规则。
2. 区域或车型规则。
3. 已发布的北美超大件暂行默认规则 `NA_OVERSIZE_TEMP_V1`。
4. 无可用已发布规则时转人工。

`NA_OVERSIZE_TEMP_V1` 必须作为明确发布、可审计的配置被选中，不能成为代码里无法追踪的静默兜底。

### 15.3 版本要求

- 每个版本记录范围、生效时间、失效时间、状态、修改人和依据。
- 已发布版本只读；修改参数创建新草稿和新版本，不原地覆盖。
- 每张报价保存使用的规则版本和完整配置快照。
- 历史报价保留原结果，不因新规则发布批量重算。
- 获得供应商正式规则后，通过供应商级版本覆盖暂行默认值，不修改核心公式代码。
- 发布前必须执行本规格第 17 节的固定回归案例。

## 16. 接入现有系统

### 16.1 数据流

```text
现有货物明细输入/识别
→ 服务端搬运单元模型
→ 单件尺寸、重量、高度和叠放规则
→ 整票最终计费托数
→ 车辆四约束校验
→ 自动结果或人工确认
→ 现有报价价格与版本快照
```

服务端计算是唯一权威。前端可以预览，但不能独立决定最终托数。

### 16.2 已知现状与改造边界

- `apps/web/src/utils/quoteParser.ts` 和 `packages/ai_assistant/quote_extractor.py` 已存在货物明细结构，继续复用。
- `apps/api/services/ai_quote_service.py::_zone_request_from_extraction` 当前只传递合计和全局最长边，实施时必须把实际搬运单元明细完整传入报价引擎。
- `packages/quote_engine/zone_models.py` 必须承载搬运单元行，不能只保留总件数、总体积、总重量和一个全局最长边。
- `packages/quote_engine/pallet_calculator.py` 继续作为现有算托入口，但其主公式改为本规格的确定性规则，不并行保留第二套超大件计算器。
- 现有 `ceil(CBM/2)` 只能保留为内部异常对照指标，不再决定实体或最终计费托数。

### 16.3 兼容与历史数据

- 历史报价保存原结果和旧规则标记，不自动回填新结果。
- 新请求只有合计值、没有实际搬运单元明细时，不得偷偷使用旧公式完成超大件自动报价，应进入人工确认。
- 如果未来需要兼容旧客户端，兼容层只能把客户明确提供的字段映射为搬运单元，不能平均分摊或猜测单件尺寸、重量和叠放能力。
- 客户总箱数继续保留在请求和记录中，但只作核对。

### 17.2 数量回归

- 100 箱打成 2 个标准托，只按 2 个搬运单元计算。

- 改变客户总箱数但不改变搬运单元明细时，尺寸托数不变；只有核对状态可能改变。
- 多条不同尺寸明细只按各自数量计算，不能使用全局最长边覆盖整票。

### 17.3 重量、高度与叠放

- 2 个标准托、总重 1,800 kg：尺寸 2、重量 4、最终 4。
- 1 个 `122×102 cm`、600 kg 单元：尺寸 1、重量 2、最终 2；内部足迹费 25、重货费 75。
- 1 个 `200×130 cm`、900 kg 木箱：尺寸 3、重量 2、最终 3；内部重货费 75。
- 单件 `500 kg` 不收重货费；`500.01 kg` 收重货费。
- 单件 `1,000 kg` 自动并收重货费；`1,000.01 kg` 转人工。
- 高度 `180 cm` 正常；`180.01 cm` 收高板费；`210 cm` 自动；`210.01 cm` 转人工。
- 同一明细有 3 个轻度超底盘搬运单元时，足迹附加费为 `25×3`，不得只收一次。
- 同一明细有 2 个同时命中轻度超底盘、高板和重货的单元时，附加费为 `(25+50+75)×2`。
- 两个明确可叠放标准托可以减少内部地板列，但尺寸计费仍为 2。
- 叠放未知或资料不完整时按不可叠放，不能减少地板列。
- 候选叠放后超过 210 cm 时先减少层数或回退为不可叠放；单件本身未超限且平放能装时不得转人工。

### 17.4 车辆

- 12 个标准托：26 尺普通装载。
- 13–14 个标准托：26 尺紧密装载。
- 15 个标准托：优先一辆 53 尺。
- 26 个标准托：53 尺普通装载。
- 27–30 个标准托：53 尺紧密装载。
- 31 个不可叠放标准托：自动拆分两辆车，最终计费托数仍为 31。
- 12 托总重 5,000 kg：26 尺非 CDL 不通过，尝试 CDL 或 53 尺。
- 总体积超过单车上限：增加车辆，不增加虚拟计费托。
- 单件超过所有车辆尺寸：转人工，不能靠加车解决。
- 需要第 4 辆车：转人工。
- 明细合计重量/体积低于容差内采用的申报合计时，比例分配后的车辆校验值之和必须精确等于采用的整票值。
- 候选车辆返回 `INCONCLUSIVE` 时转人工，不得继续升级车型；只有 `PROVEN_NOT_FIT` 才继续。
- 多个车组同时可行时，严格按车辆数、可比较基础价、总有效体积、总载重和车型编码顺序决胜。
- 禁止旋转的搬运单元只尝试原始长宽方向；允许旋转的同一单元尝试两个水平朝向。
- 排布算法在不同进程和重复运行中必须返回相同结果。

### 17.5 数据核对与输出

- 箱数、重量、体积在容差上边界时继续自动；刚超过边界时转人工。
- 客户申报重量低于明细合计时用明细；高于明细但在容差内时用申报。
- 只有部分明细填写所含箱数时，不得把部分合计与客户总箱数误判为完整差异。
- 成功页面只显示“计费托数：N”。
- 人工页面只显示“需要人工确认”，不显示推测托数。
- 普通 DTO 不得带出车辆、附加费、供应商和内部计算轨迹。

### 17.6 上线门槛

- 所有边界、公式、附加费和车辆参数来自已发布配置。
- 单元测试覆盖本节全部固定案例。
- 集成测试证明货物明细从前端/提取器完整传入 Zone Quote Engine。
- 回归测试证明不再出现“少数超长件×客户总箱数”的托数爆炸。
- 回归测试证明 `ceil(CBM/2)` 不再决定最终计费托数。
- 车辆排布、体积、重量和单件可装性测试通过。
- 规则版本与配置快照可复算相同结果。
- 历史报价没有被新规则自动重算。
- 普通销售 DTO 和页面完成内部字段泄露检查。
- 未经用户明确批准，不进入生产部署。

## 18. 暂行风险与后续校准

以下内容是已批准的暂行默认值，不应伪装成供应商正式标准：

- 150/122 cm 首次扩托线。
- 135/110 cm 轻度超尺寸线。
- 后续 5 cm 容差和面积 2% 容差。
- 25/50/50/75 的固定附加费。
- 500 kg/计费托重量当量。
- 180/210 cm 高度线。
- 26 尺和 53 尺有效尺寸、体积、载重、常规值与紧密上限。
- 最多自动拆分 3 辆车。

上线后应按供应商账单、人工复核结果和真实装车反馈记录偏差，但任何调整都必须发布新规则版本。需要重点观察：

- 尺寸托数与供应商实际计费托数的差异。
- 轻度/中度超尺寸附加费是否覆盖真实成本。
- 13–14 托和 27–30 托紧密装载的接受率。
- 500–1,000 kg 单件的装卸失败或额外收费。
- 因 5 cm、2% 容差产生的人工改价。
- 超过 3 辆车后人工方案与系统内部预估的差异。

## 19. 已批准的最终体验

销售继续在现有货物明细中录入实际搬运单元。系统按每个搬运单元计算尺寸托数，按整票重量计算重量托数，并以客户明确申报托数作为下限；随后在内部用真实尺寸、体积、重量和叠放条件验证 26 尺或 53 尺车辆。

如果数据和车辆校验全部通过，普通结果只出现一个数字：

```text
计费托数：N
```

如果缺少关键数据、单件过重过高、无法装车、数据冲突、排布不确定或需要超过 3 辆车，普通结果只显示：

```text
需要人工确认
```

客户总箱数永远只做核对，不直接乘托位；高板可以保持一个地板底座；可叠放只优化内部装车；轻微超出通过附加费吸收；明显超大按真实托盘尺寸扩展；车辆数量和车厢体积不会再次制造虚拟计费托。

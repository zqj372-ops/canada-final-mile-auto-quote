# AI 报价工具全产品重构设计规格

**状态：** 已批准，可进入实施计划

**批准日期：** 2026-08-03

**适用仓库：** `zqj372-ops/canada-final-mile-auto-quote`

**实施基线：** `origin/codex/fcl-quote-workflow-rework`（包含 Draft PR #3、提交 `7baa129`）
**产品范围：** 销售前台、运营/管理后台、加拿大末端报价、FCL 整柜报价、复核与版本、PDF、发送记录、客户结果、配置维护、管理数据

## 1. 设计结论

本次重构不是新建第二套系统，而是在现有 FastAPI、SQLAlchemy、React、报价引擎、用户权限、销售报价记录和配置模块上，建立一条可审计、可追溯、可继续处理的报价业务主线。

核心结论如下：

1. 销售前台与管理后台彻底分开：独立入口、独立导航、独立页面层级和独立权限，不在一个侧边栏里混合销售与后台功能。
2. 报价以任务驱动：销售先看“现在该做什么”，运营先看“现在要处理什么”，配置人员先看“哪些条件即将失效或缺失”。
3. `SalesQuoteRecord` 是报价业务聚合根；人工任务、版本、PDF、发送事件和客户结果都必须关联同一报价记录。
4. 加拿大末端报价允许粘贴原始询价，由系统识别字段，但重量、体积、密度、最大单件和计价结果必须根据结构化分项重新计算，绝不照搬原文声明值。
5. FCL 整柜报价只允许填写结构化表单，不提供原始文本粘贴、OCR、自然语言解析、AI 补字段或自动提交。
6. 自动报价先形成不可变 V1；运营复核不能覆盖 V1，只能形成不可变 V2。后续改价形成 V3、V4。
7. 销售不能直接修改已锁定版本的核心价格，只能发送、申请重新复核、补充资料或复制为新报价。
8. PDF、页面、复制给客户的回复、发送记录必须使用同一个公开报价版本快照。
9. PDF 生成、下载或复制都不代表已经发送。只有成功登记发送事件，报价才进入“等待客户回复”。
10. 客户档案只保存客户名称；收件人、邮箱、微信号等本次发送信息属于发送记录，不进入客户档案。
11. 运营不直接联系客户。运营确认报价后把锁定版本和客户回复交还销售；销售发送并登记客户结果。
12. 缺少已发布配置、匹配冲突、费率重叠、汇率重叠或关键数据矛盾时必须停止自动报价并进入人工处理，不得使用默认值或数组第一条继续报价。

## 2. 目标与非目标

### 2.1 目标

- 多名销售可以快速创建报价、查看自己的任务、发送报价并记录客户结果。
- 少数运营或管理员可以领取复核、要求销售补资料、发布锁定版本、维护价格条件和处理异常。
- 管理员偶尔也能创建报价，但进入销售前台时仍使用销售工作台，不把报价动作塞进后台配置页面。
- 报价记录清楚呈现“状态、下一步、当前有效版本、金额、有效期和责任人”，详情再展示询价、费用和时间线。
- 所有金额、单位、汇率、有效期、版本和动作可以追溯到具体来源和具体操作人。
- 配置维护从大表格浏览改为任务队列：优先处理到期、缺失、冲突和异常。
- 管理数据只展示商业报价结果和销售绩效，不把配置健康、系统诊断和运营积压混入经营指标。

### 2.2 非目标

- 不创建新的独立报价系统或第二套报价记录。
- 不把 `quote-pdf-builder` 的 Electron、本地存储、可编辑 JSON、账单模块或前端金额计算迁入主系统。
- 本阶段不建设订单履约模块；客户接受后只允许填写可选的外部订单号。
- 不让后台人员直接发送客户邮件或微信。
- 不让 AI 决定 FCL 价格、补全 FCL 定价字段或绕过已发布配置。
- 不用复杂图表装饰页面；数据可视化仅用于解释确有价值的趋势、结构和漏斗。

## 3. 角色、责任与权限

| 角色 | 主要入口 | 可以做 | 不可以做 |
| --- | --- | --- | --- |
| 销售 `sales` | 销售前台 | 创建报价；查看和处理自己的报价；补资料；发送；登记客户结果；复制为新报价 | 查看其他销售记录；修改已锁定价格；查看成本、供应商、内部备注和费率优先级；发布配置 |
| 运营 `operator` | 管理后台 | 查看复核队列；领取任务；要求补资料；创建复核版本；查看允许的报价记录和操作时间线；领取配置任务；编辑、保存、验证并执行结构化测试报价 | 直接联系客户；替销售标记发送；发布、停用或回滚配置；修改已锁定版本 |
| 管理员 `admin` | 管理后台，也可进入销售前台 | 运营全部能力；配置、发布、停用、回滚；用户和权限；必要时创建报价 | 绕过状态机；覆盖历史版本；绕过审计 |
| 查看者 `viewer` | 经授权的只读后台 | 查看允许的报表和记录 | 创建报价、复核、发送、修改配置 |

权限必须由服务端校验。前端的隐藏按钮只是体验优化，不是权限边界。

销售访问规则：

- 销售仅能读取和操作 `owner_user_id` 等于自己的报价；旧 `actor_user_id` 仅用于迁移兼容。
- 报价同时保存 `owner_user_id` 和 `created_by_user_id`：前者是当前报价负责人，后者是真实创建人；销售正常报价时两者相同。
- 管理员从销售前台创建报价时，默认两者均记录真实管理员身份和 `actor_role=admin`，但使用相同销售流程。若未来允许管理员替某名销售创建，必须显式选择负责人并保留管理员为创建人，不能伪装成销售。
- 运营或管理员处理复核时，所有动作记录真实用户 ID、姓名、角色和时间。

## 4. 产品信息架构

### 4.1 销售前台

销售前台仅保留三个一级入口：

1. **工作台**
   - 新建报价
   - 今日待办
   - 最近报价
2. **客户与报价**
   - 客户列表
   - 报价记录
   - 报价详情
3. **待办跟进**
   - 待补资料
   - 待发送
   - 待客户回复
   - 即将到期

销售前台不显示后台配置、诊断、学习候选、人工任务大表、供应商成本或审计技术字段。

### 4.2 管理后台

管理后台一级入口：

1. **运营工作台**
   - 待复核
   - 处理中
   - 等待销售补资料
   - 异常
2. **报价复核**
   - 复核队列
   - 复核详情
3. **报价记录**
   - 全部报价
   - 版本和发送历史
4. **规则与价格**
   - 加拿大末端规则与价格
   - FCL 规则与价格
   - 数据维护任务
   - 发布历史与回滚
5. **管理数据**
   - 报价量和金额
   - 自动报价率
   - 复核时效
   - 发送率、接受率、失单原因
   - 销售绩效
6. **用户与权限**

“基础数据”不作为一级菜单。港口、柜型、区域、城市、邮编、汇率和费率数据嵌套在“规则与价格 → 数据维护”中。

### 4.3 前后台隔离方式

- `/quote/*` 使用 `SalesApp`、`SalesShell`、销售导航和销售认证恢复流程。
- `/admin/*` 使用 `AdminApp`、`AdminShell`、后台导航和后台角色守卫。
- 两套入口可以复用同一组件库和同一 API 客户端，但不能复用导航结构或把后台链接放进销售侧边栏。
- 未登录访问任一入口时，只显示对应入口的登录界面。
- 销售登录后不自动进入后台；管理员进入销售前台时也只看到销售工作台。

## 5. 视觉与交互规范

### 5.1 视觉方向

- 背景：浅冷灰，页面内容使用白色或极浅灰卡片。
- 主色：克制的专业蓝；仅主要动作、选中状态和关键链接使用。
- 成功、警告、危险：分别使用低饱和绿、琥珀、红；不使用大面积高饱和背景。
- 圆角和阴影：中等圆角、轻边框、极轻阴影；层级主要由间距和边框表达。
- 数字：金额、重量、体积、密度使用等宽数字或 `tabular-nums`，统一右对齐。
- 密度：销售页面适度留白；后台列表更紧凑，但详情仍按清晰区块分组。

### 5.2 统一组件

必须建立并复用：

- `PageHeader`
- `StatusBadge`
- `NextActionCard`
- `MetricCard`
- `DataTable`
- `RecordCard`（窄屏）
- `FilterBar`
- `EmptyState`
- `ErrorState`
- `Timeline`
- `MoneyAmount`
- `FeeTable`
- `QuoteVersionBadge`
- `ResponsiveActionBar`
- `ConfirmDialog`

组件的业务数据来自公开 DTO，不允许组件直接读取 `result_json`、`request_json` 或内部快照。

### 5.3 响应式

- 桌面列表使用表格；宽度不足时切换为一条记录一张卡片，不使用横向挤压的桌面表格。
- 主要动作在桌面位于页头或右侧；移动端固定在底部动作栏。
- FCL 表单桌面按 2–3 列组织，移动端为单列分步表单。
- PDF 预览桌面为右侧或独立抽屉，移动端为全屏预览。
- 时间线移动端只显示关键事件标题、时间和操作人，展开后查看说明。

## 6. 销售工作台

### 6.1 首屏顺序

1. 新建报价
2. 今日待办
3. 最近报价

新建报价入口展示“加拿大末端”和“FCL 整柜”两个业务类型，并记住当前销售上次使用的类型。类型记忆只影响默认选中，不预填价格和关键业务字段。

### 6.2 今日待办排序

优先级从高到低：

1. 待销售补资料
2. 待销售发送
3. 报价即将到期
4. 已发送待客户回复且超过跟进时间

每条待办必须显示：客户名称、报价编号、业务类型、金额摘要、状态、截止时间和唯一主要动作。

### 6.3 最近报价

只显示摘要，不展示长文本或 JSON：

- 报价编号和类型
- 客户名称
- 路线或目的地
- 柜型/托盘摘要
- 当前有效版本金额
- 业务状态
- 下一步动作
- 更新时间

## 7. 客户档案与报价记录

### 7.1 客户档案

客户档案仅包含：

- `id`：系统自动生成
- `name`：必填，去除首尾空格；大小写和空格规范化后用于重名提示
- `created_at`
- `created_by_user_id`
- `updated_at`

客户档案不保存联系人、邮箱、电话、微信、地址、信用额度、标签或备注。

允许出现同名客户，但创建时提示可能重复，由销售确认。历史报价通过 `customer_id` 关联；报价版本同时冻结 `customer_name`，确保后续改名不改写历史单据。

销售侧客户目录只返回该销售创建的客户，或已关联到该销售有权访问报价的客户；运营/管理员按后台权限读取，任何客户接口都不得带出其他销售的报价或活动。客户名称点击后使用 `customer_id` 筛选“报价记录”，不另建 CRM 式客户详情页。创建/更新请求采用 `extra="forbid"`，邮箱、电话、联系人、地址和备注等额外字段返回 `422`。

### 7.2 报价列表

桌面列：

- 报价编号 / 类型
- 客户
- 路线或目的地
- 柜型与柜量 / 托盘摘要
- 当前公开合计
- 版本
- 业务状态
- 下一步动作
- 销售 / 更新时间

筛选：

- 待我处理
- 进行中
- 已结束
- 报价类型
- 日期范围
- 销售（仅有权限的后台角色）
- 关键词

API 必须服务端分页和筛选。列表只返回摘要；完整版本、询价快照、费用和时间线由详情接口读取。

### 7.3 报价详情固定结构

1. **现在该做什么**：状态、下一步、截止时间、合法动作。
2. **概览**：客户、路线、货物摘要、当前版本金额、有效期、销售、复核人。
3. **询价信息**：结构化输入快照；加拿大末端可查看原始文本证据，FCL 不显示原始询价文本区。
4. **报价明细**：公开费用、币种小计、折算合计、包含/不包含、条款和有效期。
5. **版本与处理**：版本列表、复核公开说明、补资料请求。
6. **操作记录**：提交、计价、复核、发送和客户结果时间线。

内部备注仅在后台详情的独立权限区显示，不能进入销售 DTO、客户回复或 PDF。

### 7.4 后台报价记录

后台“报价记录”是独立于复核队列的只读/审计工作区，不复用销售列表，也不把版本展开成多条报价：

- 列表始终一份 `SalesQuoteRecord` 一行，显示负责人、当前版本、状态、金额、有效期、最近动作和异常标记；版本数、发送次数用摘要字段显示。
- 详情先显示业务概览，再分成“公开报价”“内部计算与复核”“版本历史”“发送与客户结果”“审计时间线”五区；公开与内部字段不得混在同一费用表。
- 版本、文档和发送事件在报价详情内嵌套展示，不能让 V1/V2 或重复发送膨胀列表行数。
- 后台可按销售、处理人、状态、类型、日期和异常筛选；viewer 只读，operator/admin 按对象权限查看内部区。
- 原始 JSON 只允许在 `/admin/tools/*` 诊断能力中按独立权限查看，不出现在正式报价详情。

## 8. 加拿大末端报价

### 8.1 输入与识别

加拿大末端报价保留原始询价粘贴，用于识别地址、货物分项和服务需求。原始文本是证据，不是计算结果。

识别后必须呈现可编辑结构化货物行：

- 数量
- 长、宽、高
- 尺寸单位
- 重量输入模式：统一单件重量、逐件重量列表或该行总重量三选一
- 重量单位
- 包装类型

### 8.2 确定性货物计算

服务端和前端使用同一公式定义，服务端为权威：

- 单件体积：`长 × 宽 × 高`，先统一换算为米。
- 行体积：`单件体积 × 数量`。
- 行重量：统一单件重量使用 `单件重量 × 数量`；逐件重量使用每件之和；行总重量直接作为该行合计。UI 只允许三选一；识别证据若同时给出多种表达，服务端必须逐一验证数学一致后规范化，不一致立即阻止自动报价。
- 总体积：所有完整货物行体积之和。
- 总重量：所有完整货物行重量之和。
- 计费密度：`总重量 ÷ 总体积`。
- 最大单件：所有可确认单件重量的最大值；数量大于 1 且只有行总重量时不得用平均值推测最大单件，标记阻断并进入人工处理。

示例必须得到：

- 两托盘，每托盘 `120 × 100 × 125 cm`
- 体积：`2 × 1.20 × 1.00 × 1.25 = 3.00 m³`
- 重量：`785 + 800 = 1,585 kg`
- 密度：`1,585 ÷ 3.00 = 528.33 kg/m³`
- 最大单件：`800 kg`

原文声明的总重量和总体积只用于留证与一致性校验，永远不能覆盖服务端从结构化货物行聚合出的结果。若只有声明合计而没有完整货物行，或声明合计与分项计算值不一致，页面并列显示“声明值”和“计算值”并停止自动报价；销售确认、勾选或选择某个来源都不能绕过。销售可以修正识别错误的货物行后重新计算；客户原始信息本身矛盾时必须进入人工复核。不得直接采用更有利、更大或经手工确认的声明合计继续自动报价。

任一结构化货物字段被修改后：

- 立即重新计算派生值；
- 清除地址/货物确认状态；
- 使旧预检、旧价格和旧 PDF 失效；
- 重新提交后创建新版本或新计算结果。

### 8.3 地址

原始地址、标准化地址、城市、省、邮编和命中区域分开显示。搜索结果只用于确认地址，不得覆盖 Zone 价格表或 Quote Engine 金额。

## 9. FCL 整柜报价

### 9.1 入口原则

FCL 只使用结构化表单。销售页面中不得出现：

- 粘贴原始询价
- 上传文件并识别
- OCR
- AI 解析
- AI 置信度
- `raw_message`
- `extraction_notes`
- `auto_submit_when_complete`

现有加拿大末端 AI 识别能力不受影响。

该禁令同时适用于后端：FCL 创建 DTO 只接受 `customer_id` 和类型化 `confirmed_fields`，设置 `extra="forbid"`；生产路由和服务不得调用 FCL extractor、OCR、LLM 或默认配置。提交 `raw_message`、`extraction_notes`、`confidence`、`auto_submit_when_complete` 等字段必须返回 `422`，自动测试同时断言解析器和模型客户端调用次数为 0。

### 9.2 表单步骤

#### 第一步：路线与服务范围

- 客户名称（从极简客户档案选择或新建）
- POL
- POD
- 服务范围
- 目标 ETD（自动匹配费率时必填）
- 预计到货日（可选）
- 船东偏好（可选）
- 服务偏好（可选）
- 船名（独立字段，可选，不复用服务偏好）
- 航次（独立字段，可选，不复用服务偏好）

首期只保留能够完整报价的服务范围。若 `door-to-port` 或 `door-to-door` 没有中国提货地址、时间和装货条件的完整规则，则从表单移除，不能只展示选项却不计价。

#### 第二步：柜型与货物

- 柜型
- 柜量
- 货物名称
- 分项尺寸、件数和重量
- 声明总重量、总体积、总件数（仅留证和一致性校验，不能成为自动计价输入）
- 货值与币种（条件必填）
- 原产国、HS Code（条件必填）
- 是否可叠放
- 木包装状态
- 特殊货物属性
- 危险品/SDS/UN 信息（条件必填）

#### 第三步：时间、报关与进口条件

- 备货日期
- 贸易条款
- 出口报关方式
- 是否已有进口商
- 进口商法定名称（条件必填）
- BN/RM、CARM 状态
- 报关行选择
- 税费口径
- 时效偏好与严格程度

#### 第四步：确认并提交

- 显示所有结构化字段摘要
- 显示系统重新计算的重量、体积和冲突
- 显示尚未满足的已发布必填条件
- 销售确认资料真实性后提交

### 9.3 自动报价条件

自动报价只有在以下条件全部满足时执行：

- 存在已发布 FCL 配置且版本号大于 0；
- 目标 ETD 可用于选择费率；
- 所有已发布必填字段满足；
- 货物分项完整且声明合计无冲突；
- 每个柜型恰好匹配一组可用费率；只有候选在船东、服务或适用范围维度确实不同且业务规则明确时，才允许按优先级得到唯一结果；
- 无费率重叠；
- 所需汇率唯一且在定价日期有效；
- 特殊货物属性与费率适用范围一致；
- 所有费用规则可确定性计算。

任一条件不满足则进入 `pending_review`，生成中文原因和解决建议，并创建关联人工任务。

## 10. 定价与计算规则

### 10.1 金额精度

- 所有后端计算使用 `Decimal`。
- 单价保留原始精度；先乘数量，再将行金额按货币规则舍入。
- 测试用例：`0.005 × 1000 kg = 5.00`，不能先把单价舍入为 `0.01` 再得到 `10.00`。

### 10.2 费用作用域

每条费用必须有稳定 `fee_id` 和明确作用域：

- `per_container`：按对应柜型数量计算。
- `per_shipment`：整票只收一次，即使有 `1×20GP + 1×40HQ`。
- `per_piece`
- `per_kg`
- `per_cbm`

`markup_fixed` 定义为整票固定加价，只应用一次。百分比加价作用于明确的可加价费用基数。前端文案、配置校验和引擎含义必须一致。

### 10.3 日期与有效期

- 费率匹配日期为业务定价日期；FCL 优先使用目标 ETD。
- 报价有效期为以下日期中最早者：默认报价有效期、全部命中费率到期日、全部使用汇率到期日。
- 报价过期后禁止发送；只能复制为新报价并重新计算。

### 10.4 冲突和缺失

以下情况必须 fail closed：

- 无已发布配置；
- 配置发布版本为 0；
- 完整适用范围相同且生效日期重叠的费率，无论优先级是否不同；
- 汇率生效期重叠；
- 费率或汇率已过期；
- 特殊货物不在费率适用范围；
- 货物声明与计算冲突；
- `service_stages` 被提交但没有真实计价语义；
- `display_mode=merged` 被配置但没有明确合并目标和金额语义。

首期如果不实现真实分段计价，则从公共表单和配置中删除 `service_stages`。首期如果不实现真实合并显示，则禁止发布 `merged`，不得只保留表面字段。

## 11. 报价状态机

### 11.1 业务状态

| 状态 | 中文 | 责任人 | 允许的主要动作 |
| --- | --- | --- | --- |
| `draft` | 草稿 | 销售 | 编辑、归档草稿、提交 |
| `pending_review` | 待后台处理 | 运营 | 领取、取消 |
| `in_review` | 后台处理中 | 运营 | 要求补资料、发布复核版本、取消 |
| `needs_sales_info` | 待销售补资料 | 销售 | 补资料并重新提交、取消 |
| `ready_to_send` | 待销售发送 | 销售 | 生成/预览 PDF、复制客户回复、发送、申请重新复核、取消 |
| `sent` | 已发送，待客户回复 | 销售 | 登记接受、变更、拒绝；登记再次发送；标记过期或取消 |
| `accepted` | 客户已接受 | 只读 | 查看接受记录、复制为新报价 |
| `change_requested` | 客户要求调整 | 销售 | 创建下一草稿版本并补充变更内容 |
| `rejected` | 客户未接受 | 只读 | 查看原因、复制为新报价 |
| `expired` | 已过期 | 只读 | 复制为新报价 |
| `cancelled` | 已取消 | 只读 | 复制为新报价 |
| `legacy_unclassified` | 历史待核对 | 有权限的后台 | 查看迁移证据、核对后归档或复制为新报价；不得直接发送 |

`pricing_status` 如保留，只描述自动计价结果，不替代 `workflow_status`。销售页面只显示一个业务状态和一个下一步动作。

报价主流程、人工任务、文档生成、发送尝试和客户结果分别使用独立状态字段；禁止把 `pending/succeeded/failed` 等发送状态写进 `workflow_status`。

### 11.2 状态转换

```text
draft
  ├─ 自动报价成功 → ready_to_send（创建并锁定 V1）
  └─ 需要人工 → pending_review（创建并锁定不可发送 V1）→ in_review
                                  ├─ needs_sales_info → pending_review
                                  ├─ ready_to_send（创建并锁定 V2/Vn）
                                  └─ cancelled

ready_to_send
  ├─ 发送成功登记 → sent
  ├─ 申请重新复核 → pending_review
  └─ cancelled

sent
  ├─ accepted
  ├─ change_requested → draft（创建下一工作草稿；提交后重新计价并进入 ready_to_send 或 pending_review）
  ├─ rejected
  ├─ expired
  └─ cancelled
```

所有转换由服务端动作接口执行。销售取消、后台取消、自动到期和历史核对都是显式受审计动作；到期由可重复执行的服务端 reconciliation job 按当前锁定版本有效期推进。非法转换返回 `409`；重复请求使用幂等键返回原结果；并发版本冲突返回 `409`，不得覆盖更新。

## 12. 报价版本与快照

### 12.1 版本规则

- 每次正式提交都创建锁定 V1：自动计价成功时 `sendable=true` 并进入 `ready_to_send`；需要人工时 `sendable=false`，保留结构化输入、服务端计算值和失败原因并进入 `pending_review`。
- 运营基于不可发送 V1 复核时创建锁定且可发送的 V2，不修改 V1；后续轮次同样只追加 Vn。
- 客户要求变更后创建 V3 草稿并设置 `working_version_id`，此时 `current_version_id` 仍指向已发送 V2。销售编辑并提交草稿时，服务端按业务类型重新计算：成功则锁定 V3、切换 current 并进入 `ready_to_send`；需人工则锁定不可发送 V3、切换 current 并进入 `pending_review`，运营再创建可发送 V4。
- 每个版本有唯一 `version_no`，同一报价内递增。
- `SalesQuoteRecord.current_version_id` 只指向最近锁定版本；`working_version_id` 只指向唯一草稿，锁定或归档后清空。
- 版本保存 `lifecycle=draft|locked`、`sendable`、`version_revision`、`locked_at` 和 `locked_by_user_id`；PDF 和发送只允许当前、锁定、可发送且未过期的版本。
- 草稿可按 revision 更新；锁定版本由数据库约束或触发器与 ORM 防护共同禁止更新，只能创建新版本。

### 12.2 版本内容

每个版本同时保存：

- `internal_snapshot_json`：后台可见的完整计算依据，严格受权限保护。
- `public_snapshot_json`：客户可见公开快照，只包含允许字段。
- 冻结的 `customer_name`：后续客户改名不改写历史页面、回复或 PDF。
- 客户回复正文。
- 报价有效期。
- 快照 SHA-256。
- 创建来源：自动、运营复核、客户变更、重新复核。
- 创建人和创建时间。

公开快照使用递归 allowlist。嵌套费用行不得泄露：供应商、成本、`source`、`priority`、`rate_card_id`、`internal_note`、内部汇率源、内部配置或匹配候选。

## 13. 运营复核闭环

### 13.1 队列

默认先显示：

- 超时待处理
- 即将过期
- 计价冲突
- 等待补资料后重新提交
- 普通待处理

支持按报价编号、路线、客户、销售、处理人、原因和提交时间筛选。

### 13.2 复核详情

从上到下：

1. Quote ID、客户、销售、状态、提交时间、超时提醒。
2. 路线、柜型柜量、货物计算、目标 ETD、服务范围。
3. 系统计算结果、未自动报价原因和中文解决建议。
4. 费用和费率依据，仅后台可见。
5. 复核表单：公开费用行、明确的人工换汇依据、服务端派生的币种小计与折算总价、有效期、客户条款、客户回复、公开说明、内部备注。
6. 版本对比：V1 与待发布 V2 的公开字段差异。
7. 时间线。

动作：

- 领取处理
- 要求销售补资料（说明必填）
- 确认并发布新版本（二次确认）
- 取消（原因必填）

发布新版本时必须在同一数据库事务中：锁定新版本、更新 `current_version_id`、更新任务、更新报价状态、追加时间线和审计记录。任一步失败全部回滚。

复核提交请求不得接受客户端提供的 `totals_by_currency` 或 `converted_total`。服务端必须从公开费用行重新按币种汇总，并仅使用类型化、可审计的人工换汇依据计算折算合计；客户端夹带或篡改合计字段返回 `422`。要求补资料的请求按 `quote_type` 使用 FCL/加拿大末端 discriminated union，两类都必须重新执行对应的服务端货物计算和报价引擎。

## 14. PDF、发送与客户结果

### 14.1 `quote-pdf-builder` 迁移边界

复用内容：

- A4 报价单信息层级和视觉布局；
- 费用明细、币种小计和折算合计的展示方式；
- 预览 iframe 的交互思路；
- 中文金额、数量、币种格式化规则；
- 模板版本概念。

不复用内容：

- Electron 主进程；
- 本机 `localStorage`；
- JSON/PDF 内嵌可编辑业务数据；
- 前端重新计算金额；
- 账单、收款和费用编辑功能；
- 客户自行修改已锁定报价。

### 14.2 PDF 数据契约

PDF 只能从业务状态为 `ready_to_send` 的当前、锁定、`sendable=true`、未过期版本的 `public_snapshot_json` 生成。后端生成并持久化：

- `quote_version_id`
- `document_type=quote_pdf`
- `template_version`
- `renderer_version`
- `storage_key`
- `mime_type`
- `size_bytes`
- `sha256`
- `version_snapshot_sha256`
- `created_by_user_id`
- `created_at`

模板和 renderer 版本只属于 `QuoteDocument`，不写入 `QuoteVersion`。生成接口是“服务端生成”而非“上传”：请求体采用 `extra="forbid"`，最多接受服务端模板注册表中的 `template_key`，幂等键只在 header；金额、费用行、HTML、快照、文件名主体、renderer 和 `storage_key` 一律拒绝。未知模板返回 `422`，服务端始终按 URL 重新读取版本快照。

如果当前版本或模板变化，旧 PDF 的派生 `sendable_now=false`，下一次发送必须重新生成；历史文档和历史发送事件始终不可变、可读，不能因“非当前”被覆盖或删除。复制客户回复正文也只读取当前版本的只读字段，复制不创建发送事件。

### 14.3 发送记录

每次发送独立记录：

- 报价版本
- PDF 文档
- 渠道：邮件、微信、企业微信、其他
- 收件信息 JSON
- 可选消息摘要
- 状态：准备中、成功、失败、待对账
- 外部服务 ID（如有）
- 失败原因
- 幂等键
- 操作人和时间

收件人只保存在发送记录。下载 PDF、复制回复、打开预览均不创建成功发送事件。

在线发送先以唯一幂等键持久化带 lease 的 `pending` 尝试，再调用渠道；支持幂等的渠道接收同一键，SMTP 使用稳定 `Message-ID`。只有外部渠道成功且确认事务完成后，才写入成功事件并把报价转为 `sent`。provider 已返回但数据库确认失败时，记录保持 pending，由恢复任务先转为 `unknown`，同一键不得再次调用渠道；管理员通过受审计的对账动作确认 delivered/failed。
线下发送：销售下载或复制后，必须点击“登记线下已发送”，填写渠道、收件信息和实际发送时间，系统才进入 `sent`。

发送成功后自动创建跟进待办。每个报价最多一个开放跟进；再次成功发送保留全部发送事件，并更新/重新绑定现有开放跟进的截止时间，不堆叠重复开放任务。

### 14.4 客户结果

- **接受**：一次性记录接受时间、`note` 和可选 `external_order_reference`；报价结束，结束后订单号不另设静默编辑动作。
- **要求调整**：记录 `change_request_text`，保留已发送版本和 PDF，创建下一版本草稿；涉及价格、路线、柜型、服务范围、货物或时间的变更必须重新复核或重新自动计价。
- **拒绝**：记录 `reason_category` 和可选 `note`；报价结束。
- **暂无回复**：不是结束状态，只更新跟进记录。

失单原因分类固定为：价格、时效、服务范围、客户取消、竞争对手、资料不全、其他。

### 14.5 异常边界

- PDF 生成失败：不创建可发送文档，不推进状态。
- 发送失败：记录失败事件，但不进入 `sent`，不创建成功跟进。
- 报价已过期：阻止发送。
- PDF 对应旧版本：阻止发送。
- 文档哈希与版本快照不一致：阻止发送并告警。
- 同一幂等键重复请求：返回原结果，不重复发送。
- `pending/unknown` 发送只能通过对账动作结束，不允许自动重发。

## 15. 规则、价格与数据维护

### 15.1 任务化首页

规则与价格首页优先显示维护任务，而不是完整费率大表：

- 7 天内到期费率
- 已过期仍启用费率
- 缺失路线/柜型
- 重叠费率
- 汇率过期或重叠
- 特殊货物适用范围缺失
- 草稿未验证
- 已验证未发布
- 发布冲突

每条任务显示影响范围、严重程度、建议动作、负责人和截止时间。

### 15.2 发布流程

固定流程：

1. 创建草稿版本。
2. 修改必要条件。
3. 保存当前草稿。
4. 校验当前保存版本。
5. 运行结构化测试报价。
6. 原子发布同一版本。

页面必须明确显示“有未保存修改”。发布接口带草稿版本或 ETag；若校验版本与待发布版本不同，返回 `409`。

### 15.3 已发布配置

- 已发布版本只读。
- 新修改生成新草稿，不原地编辑。
- 支持审计化停用、替代和回滚。
- 紧急停用必须记录原因、操作人和时间。
- 批量发布要么全部成功，要么全部失败。
- 每个 release 有明确 `scope`；`(scope, version)` 唯一。每个 scope 由单独的 release head 保存 `current_release_id` 和 revision，发布事务锁住该 head，不能只依赖查询当前 release 后再写入。
- 并发发布用 head 行锁和 revision 双重保护，不能产生重复版本号、两个 current 或部分切换。

## 16. 管理数据

### 16.1 只展示经营结果

管理数据包括：

- 报价量
- 已发送量和发送率
- 客户接受量和接受率
- 报价金额（按币种分开，不无依据相加）
- 自动报价率
- 人工复核率
- 首次响应时长
- 复核时长
- 从报价到发送时长
- 从发送到客户结果时长
- 即将过期但未发送数量
- 失单原因分布
- 销售个人/团队报价、发送和接受情况

配置健康属于“规则与价格”，复核积压属于“运营工作台”，技术诊断属于系统管理；三者不放进管理数据。

### 16.2 指标定义

- 经营指标默认去重键都是唯一 `SalesQuoteRecord.id`；同一报价的 V1/V2/Vn、重复进入状态或重复发送不得重复计数。版本数、复核轮次和发送次数只能作为单独标明的过程指标。
- 报价量：所选期间首次正式提交的 distinct `SalesQuoteRecord.id`。
- 自动报价率：首次形成可发送版本且此前无需人工复核的 distinct 报价数 ÷ 所有正式提交的 distinct 报价数。
- 发送率：存在至少一个成功发送事件的 distinct 报价数 ÷ 至少一次进入 `ready_to_send` 的 distinct 报价数。
- 接受率：最终结果为 accepted 的 distinct 报价数 ÷ 最终结果为 accepted 或 rejected 的 distinct 报价数；分母不含暂无回复和仅要求调整。
- 首次响应时长：首次提交到首次形成可发送版本的时间。
- 复核时长：进入 `pending_review` 到形成可发送版本或取消的时间。
- 发送时长：进入 `ready_to_send` 到首次成功发送的时间。

每个指标必须显示时间范围、样本数和口径说明。金额按币种展示；只有存在版本冻结的合法汇率快照时才展示折算金额。

### 16.3 可视化

- 趋势：折线图，最多比较 2–3 个同口径指标。
- 流程：报价 → 可发送 → 已发送 → 有结果 → 接受的漏斗。
- 构成：失单原因使用横向条形图，避免饼图标签拥挤。
- 销售对比：表格为主，必要时用排序条形图。
- 所有图表支持查看支撑明细；不得用图表代替异常任务列表。

## 18. 数据模型方向

### 18.1 保留并扩展

- `SalesQuoteRecord`：聚合根；在 `0022` 已有 `workflow_status`、`revision`、`valid_until`、`sent_at`、`closed_at`，后续只增加 `customer_id`、`owner_user_id`、`created_by_user_id`、`current_version_id` 和 `working_version_id`。
- `ManualQuoteTask`：工作项，统一使用 `record_id`、`quote_version_id` 和 `resolved_version_id`。
- `QuoteWorkflowEvent`：业务时间线，增加版本、任务、发送和幂等关联。

### 18.2 新增

- `Customer`
- `QuoteVersion`
- `QuoteDocument`
- `QuoteSendEvent`
- `QuoteFollowUpTask`

客户结果用类型化 `QuoteWorkflowEvent` 表达，并绑定报价版本和发送事件；不再创建另一张无关联“结果表”。

### 18.3 关键约束

- `(record_id, version_no)` 唯一。
- 锁定版本由数据库层和 ORM 层共同禁止更新。
- `current_version_id` 和 `working_version_id` 必须通过复合外键或等价数据库约束属于同一 `record_id`；人工任务的版本关联同样受数据库约束。
- `parent_version_id` 必须指向同一 `record_id`，不能跨报价建立版本链。
- `current_version_id` 只能指向 locked；`working_version_id` 只能指向 draft；一个报价最多一个工作草稿。
- 文档必须属于指定版本。
- 成功发送事件创建时必须绑定当时的 current、有效、未过期版本和对应文档；后续改单产生新 current 时，历史发送事件仍永久绑定原版本与文档。
- 幂等键在动作作用域内唯一。
- 公开快照和文档哈希必填。
- 删除报价采用受控归档，不级联删除已发送版本和文档。

### 18.4 字段命名与迁移链

- 所有用户外键统一使用 `*_user_id`，所有报价子实体统一使用 `record_id`，版本使用 `quote_version_id`，发送使用 `quote_send_event_id`；API、ORM 和迁移不得混用 `created_by`、`external_reference` 或 `sales_quote_record_id` 等第二套命名。
- 实施基线必须先整合 `origin/codex/fcl-quote-workflow-rework`，确认唯一 head `0022_quote_workflow`，其 `down_revision="0021_fcl_quote_closed_loop"`。
- 后续迁移固定为单链且一经应用不可改写：`0023_customers → 0024_fcl_rate_contracts → 0025_quote_versions → 0026_fcl_pricing_releases → 0027_pricing_maintenance_tasks → 0028_quote_documents → 0029_quote_delivery`。
- 旧数据先生成审计报告。只有可验证的发送、结果、任务或 actor 证据才回填对应状态和责任人；API key、actor 缺失或状态无法判断的记录使用 `legacy_unclassified` 并进入迁移异常清单。不得把 `0022` 的默认 `pending_review` 当作历史事实。
- 历史回填版本使用 `source=legacy_backfill`、`sendable=false`，除非有完整且可验证的公开报价与发送证据；缺失 owner 的历史记录允许 owner 暂为空，但所有新记录服务端强制 owner 非空。

## 19. 审计、安全与隐私

- 所有写动作记录真实 actor、角色、时间、来源版本、前后状态和幂等键。
- 销售公开 DTO 采用递归 allowlist；禁止通过嵌套费用或 metadata 泄露内部字段。销售时间线使用独立 `PublicTimelineEvent`，事件类型只允许 `submitted/info_requested/info_submitted/version_ready/sent/accepted/change_requested/rejected/expired/cancelled`，字段只允许公开说明、actor 展示名和时间；后台审计 DTO 才能包含内部事件字段，收件信息仍按权限单独读取。
- PDF 模板只渲染 allowlist 字段并转义 HTML。
- 预览 iframe 使用最小 sandbox 权限，不允许脚本。
- 下载文档前再次校验记录所有权或后台权限。
- 存储路径不从用户输入直接拼接。
- 日志不记录收件人完整联系方式、客户敏感内容或内部成本明细。
- 配置发布、回滚、紧急停用和用户权限变更必须进入审计日志。

## 20. 完整验收场景

### 20.1 加拿大末端自动报价

1. 销售粘贴询价。
2. 系统识别两托盘和地址。
3. 页面显示计算的 `3.00 m³ / 1,585 kg / 528.33 kg/m³ / 800 kg`。
4. 销售确认结构化数据。
5. 服务端重新计算并生成锁定 V1。
6. 销售生成 PDF、成功发送并登记。
7. 客户接受，报价结束；时间线完整。

加拿大末端若因货物冲突、地址或规则缺失进入人工处理，也必须先冻结不可发送 V1。运营要求补资料时，销售在同一报价修改结构化货物/地址并重新提交，服务端重新运行 `cargo_metrics` 和 Zone Quote Engine；销售确认不能绕过冲突，运营最终只能追加可发送 Vn。

### 20.2 FCL 自动报价

1. 销售只填写结构化分步表单。
2. 已发布配置、ETD、费率和汇率唯一匹配。
3. 系统计算并创建锁定 V1。
4. 页面、PDF、复制回复金额完全一致。
5. 成功发送后进入 `sent`。

### 20.3 FCL 人工复核

1. 结构化提交因无唯一费率进入 `pending_review`。
2. 运营领取进入 `in_review`。
3. 运营要求补资料，销售在同一报价补充并重提。
4. 运营形成公开费用、条款和客户回复，发布锁定 V2。
5. 销售只能发送 V2，不能修改 V2 价格。
6. 客户要求调整，已发送 V2/PDF 保留，系统创建 V3 草稿。
7. 销售编辑 V3 并重新提交；自动成功则锁定可发送 V3，需人工则锁定不可发送 V3 并由运营创建可发送 V4。

### 20.4 失败场景

- 无发布配置：进入人工，不使用默认配置。
- 声明重量与分项冲突：阻止自动报价。
- 只有声明合计或销售勾选确认冲突：仍阻止自动报价。
- 两条汇率重叠：阻止自动报价。
- PDF 生成失败：状态仍为 `ready_to_send`。
- 发送失败：不进入 `sent`。
- 旧版本 PDF：禁止发送。
- 运营发布事务中任一步失败：任务、版本、记录和事件全部回滚。
- 销售访问他人记录：返回 `403`。
- 并发发布同一草稿：一个成功，另一个返回 `409`。
- provider 已发送但数据库确认失败：同一幂等键不得再次调用渠道，事件进入待对账并由管理员确认。

## 21. 上线门槛

以下全部满足才可申请合并或部署：

- 后端全量测试通过。
- FCL、加拿大末端计算、状态机、版本、RBAC、配置发布、PDF、发送和客户结果定向测试通过。
- 前端组件测试和生产构建通过。
- Alembic 只有一个 head。
- 在真实 PostgreSQL 临时库执行 `upgrade head → 数据断言 → downgrade 0022_quote_workflow → upgrade head → 数据断言`。
- 浏览器人工走通加拿大末端自动报价、FCL 自动报价、FCL 补资料复核、发送失败、客户变更五条路径。
- 销售 DTO、PDF 和网络响应完成内部字段泄露检查。
- 不存在未定义状态、未使用路由、占位按钮或假分页。
- Draft PR 列出完成项、未完成项、测试证据和残余风险。
- 未经用户明确批准，不合并 `main`，不部署生产。

## 22. 已批准的最终体验

本规格对应用户逐步确认的最终方向：任务驱动的独立销售前台和管理后台；客户档案仅名称；加拿大末端识别后必须重新计算；FCL 仅结构化表单；每次正式提交冻结 V1、失败版本不可发送、复核只追加 V2/Vn；销售负责发送和客户结果；后台负责复核和配置；配置任务化；销售与后台报价记录均一报价一行、详情分区；PDF、发送、跟进和客户变更形成可审计闭环。
